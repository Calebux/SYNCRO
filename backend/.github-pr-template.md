# Contract Storage TTL/Archival Strategy Implementation

**Closes:** #1068  
**Type:** Feature - Hardening  
**Impact:** Backend, Infrastructure

---

## Summary

This PR implements a comprehensive Time-To-Live (TTL) and archival strategy for SYNCRO contract entries on Stellar Soroban. It addresses:

- **State Rent Minimization**: Automated TTL extension before expiration prevents costly state rent charges
- **Safe Cleanup**: Privacy-preserving archival with encrypted off-chain snapshots and on-chain proof
- **Auditability**: Tamper-evident logging of all lifecycle events
- **Operational Safety**: Rate limiting, batching, gas budgeting, and full idempotency

## Key Features

### 1. Automated TTL Bumping
- **Daily Worker**: Scans for entries with TTL < 7 days (configurable)
- **Rate Limiting**: Max 2 bumps per entry per day (configurable)
- **Batching**: Process up to 50 entries per run with gas budgeting
- **Idempotent**: Safe to re-run; calls with same TTL succeed silently

### 2. Privacy-Preserving Archival
- **Detection**: Identifies expired entries after 14-day grace period
- **Snapshots**: Creates JSON snapshots with sensitive field redaction
- **Encryption**: AES-256-GCM encryption with random IV
- **Storage**: Multi-backend support (S3, local filesystem, IPFS)
- **Proof**: Records snapshot hash on-chain via `mark_archived` call
- **Metadata**: Persists archival records with retention windows (1 year default)

### 3. Audit Trail
- **Tamper-Evident**: Cryptographic hash chain prevents log tampering
- **Privacy-Safe**: Logs use hashed entry keys, redacted fields
- **Complete**: All mutations logged with timestamps, actors, outcomes
- **Queryable**: Support for audit log retrieval and verification

### 4. Safety & Control
- **Rate Limiting**: Per-entry and per-batch limits prevent runaway costs
- **Gas Budgeting**: Cumulative gas tracking stops batch at limit
- **Dry-Run Mode**: Test configuration without on-chain calls
- **Error Handling**: Exponential backoff, partial-batch resilience
- **Manual Override**: Admin endpoints for emergency intervention

## Configuration

All parameters in `backend/config/ttl.json`, overridable via environment:

```bash
TTL_BUMP_THRESHOLD_DAYS=7              # Bump when < 7 days left
TTL_DEFAULT_EXTENSION_DAYS=90          # Extend by 90 days
TTL_MIN_BUMP_INTERVAL_HOURS=24         # Min between bumps
TTL_ARCHIVAL_GRACE_PERIOD_DAYS=14      # Wait after expiration
TTL_ARCHIVAL_RETENTION_WINDOW_DAYS=365 # Keep snapshots 1 year
TTL_BATCH_SIZE=50                      # Entries per run
TTL_MAX_GAS_PER_BATCH=10000000         # Max gas per batch
TTL_WORKER_SCHEDULE="0 0 * * *"        # Midnight UTC
TTL_ARCHIVAL_SCHEDULE="0 2 * * *"      # 2 AM UTC
TTL_SNAPSHOT_STORAGE="s3"              # s3, ipfs, or local
TTL_SNAPSHOT_ENCRYPTION=true           # Enable encryption
TTL_DRY_RUN=false                       # Test mode
```

## Deployment

### Prerequisites
- Node.js v18+
- PostgreSQL (for archival_index table)
- S3 bucket (if using S3 backend) or local storage
- Encryption key (32 bytes in hex) in AWS Secrets Manager
- Worker signing key for blockchain calls

### Steps
1. Run migrations to create `archival_index` table
2. Configure environment variables (see Configuration section)
3. Deploy application
4. Enable workers: `TTL_ENABLE_TTL_BUMPING=true TTL_ENABLE_ARCHIVAL=true`
5. Monitor logs: `docker logs -f | grep -E "TTL|archival"`

### Monitoring
- Watch logs for worker errors
- Track audit events: `SELECT COUNT(*) FROM audit_logs WHERE action LIKE 'extend_ttl%'`
- Monitor gas costs and latency
- Alert on worker failures (3+ consecutive failures)

## Known Limitations

1. **Manual Entry Scanning**: Currently reads from database; should implement contract RPC enumeration in future
2. **Read-Only TTL Query**: `getTTL` uses simulation; full implementation needs contract entrypoint
3. **Local Key Management**: Production should use AWS Secrets Manager for encryption keys
4. **No Auto-Restore**: Recovery of archived entries requires manual admin action

See `IMPLEMENTATION_SUMMARY.md` for future enhancements.

## Performance Impact

- **Memory**: ~50KB per worker instance (lightweight)
- **Database**: Archival index table; ~100 bytes per archived entry
- **Network**: 1-2 contract calls per entry per bump cycle (configurable batch size)
- **Storage**: Off-chain snapshots; size depends on entry complexity (typically < 10KB)

---

## Security Considerations

- **Encryption**: AES-256-GCM for at-rest snapshot encryption
- **Signing**: Worker operations require authorized signing key
- **Privacy**: PII redacted in snapshots (email, SSN, payment details, address, DOB)
- **Audit**: All operations logged in tamper-evident hash chain
- **Rate Limiting**: Prevents DoS attacks via repeated bumps

See `ttl-security.test.ts` for full security test coverage.
