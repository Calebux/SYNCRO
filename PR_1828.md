# feat: provider discovery manifest (#1828)

Closes #1828

---

## Problem

An agent visiting a new SYNCRO provider API had no way to discover programmatically:
- which gateway URL to target for paid calls
- which payment assets the provider accepts (and on which network)
- what routes exist and what each one costs
- which Ed25519 public key to trust for receipt signature verification
- where to find the provider's terms of service

This forced consumers to either hard-code configuration or rely on out-of-band documentation, making automated agent integration fragile.

---

## What this PR does, end-to-end

### 1. JSON Schema — `packages/shared/src/schemas/provider-manifest.schema.json`

A `draft-07` JSON Schema defining the `SyncroProviderManifest` v1.0 wire shape.
Fields:

| Field | Description |
|---|---|
| `manifestVersion` | Schema version (`"1.0"`). Consumers must reject unknown major versions. |
| `providerId` | Provider UUID |
| `identity` | Human-readable provider identity |
| `gatewayUrl` | Base URL of the SYNCRO gateway |
| `mode` | `"staging"` or `"production"` |
| `acceptedAssets[]` | Payment assets in preference order (asset code, network, scheme, optional contract address) |
| `routes[]` | Every registered paid route — pathPattern, method, unit, priceStroops, maxBillableUnits, current rateCardVersion |
| `receiptKeys[]` | Ed25519 public keys for receipt verification — `"current"` + `"previous"` after rotation (issue #1702) |
| `termsUrl` | URL of the provider's API agreement |
| `generatedAt` | ISO 8601 generation timestamp |

### 2. Backend manifest builder — `backend/src/v3/provider-manifest.ts`

`buildProviderManifest(providerId, providerStore, receiptService)` assembles a live manifest from the in-memory provider store and the `ReceiptService`. It:
- Returns `null` for unknown providers (route handler → 404).
- Derives `acceptedAssets` from the provider's `mode` and the `STELLAR_NETWORK` / `SOROBAN_CONTRACT_ADDRESS` env vars — staging gets XLM/testnet, production gets USDC+XLM/mainnet.
- Resolves the `gatewayUrl` from `SYNCRO_GATEWAY_URL` or `BACKEND_URL`, with a stable `https://api.syncro.dev` fallback.
- Resolves `termsUrl` from the provider's `agreementTerms` field when it is a URL, otherwise falls back to `SYNCRO_TERMS_URL` env var.
- Includes both `"current"` and `"previous"` receipt keys from `receiptService.getReceiptPublicKeys()` — this means the manifest automatically tracks key rotation state from issue #1702 without any extra work.
- Never includes secret material (no `providerSecret`, no payout address, no rate-limit internals).

### 3. Backend route handler — `backend/src/routes/v3/provider-manifest.ts`

A single `serveManifest` handler mounted at two paths in `backend/src/index.ts`:

```
GET /api/v3/providers/:providerId/manifest
GET /.well-known/syncro/:providerId
```

Both are **public** (no auth). The handler sets `Cache-Control: public, max-age=300, stale-while-revalidate=60` so agents cache for 5 minutes without hammering the server.

### 4. SDK provider middleware — `sdk/src/provider/middleware.ts`

The `metered()` middleware now accepts an optional `manifest` option:

```ts
metered(pricing, {
  manifest: () => buildProviderManifest(providerId, store, receiptService),
})
```

When present the middleware **intercepts** `GET /__syncro/manifest` and `GET /.well-known/syncro/:providerId` **before** the payment check and returns the manifest with the same 5-minute cache header. This means any Express app using the `metered()` middleware automatically becomes self-describing with no extra route registration.

New types exported from `@syncro/sdk` root:
- `SyncroProviderManifest`
- `ManifestAssetDescriptor`
- `ManifestRouteDescriptor`
- `ManifestReceiptKeyEntry`

### 5. Consumer SDK manifest client — `sdk/src/v3/manifest-client.ts`

`ManifestClient` — a fetch-and-cache client exported from `@syncro/sdk/v3`:

```ts
import { ManifestClient, manifestClient } from '@syncro/sdk/v3';

// Using the shared default instance
const manifest = await manifestClient.fetch('https://api.example.com', providerId);

// Key lookup for receipt verification
const key = ManifestClient.currentReceiptKey(manifest);

// Route price lookup (no network call)
const route = ManifestClient.matchRoute(manifest, 'POST', '/v1/chat');
console.log(`Price: ${route?.priceStroops} stroops per ${route?.unit}`);
```

Internals:
- In-process LRU-style cache keyed by `{baseUrl}:{providerId}`, TTL 300 s (matches server `max-age`).
- Tries `GET /api/v3/providers/:providerId/manifest` first, then `GET /.well-known/syncro/:providerId` as fallback.
- Validates `manifestVersion === "1.0"` and required fields before returning; throws `ManifestValidationError` for malformed responses.
- `invalidate(baseUrl, providerId)` and `invalidateAll()` for explicit cache busting after rotation events.
- `ManifestClient.allValidReceiptKeys(manifest)` returns both `current` and `previous` keys — needed during the rotation dispute window (#1702).

### 6. `createPaidFetch` manifest integration — `sdk/src/v3/paid-fetch.ts`

`PaidFetchConfig` gains two new optional fields:

| Field | Purpose |
|---|---|
| `manifest` | Static `SyncroProviderManifest` or async factory. Resolved once and cached for the lifetime of the fetch function. |
| `manifestPriceTolerance` | Max fractional overage (0 = exact, 0.05 = 5%) before a 402 challenge price is refused as a potential price-tamper. |

Behaviour when `manifest` is provided:
1. **Gateway public key** — derived from the manifest's `'current'` receipt key PEM. An explicit `gatewayPublicKey` always overrides this.
2. **Quote pre-check** — after verifying the gateway signature, the challenge `amount` is compared to the manifest's route `priceStroops`. If the challenge price exceeds the manifest price beyond `manifestPriceTolerance`, the payment is silently refused (original 402 response returned to the caller). This prevents a compromised gateway from inflating prices unnoticed.

```ts
const manifest = await manifestClient.fetch(providerUrl, providerId);
const paidFetch = createPaidFetch({
  spendingKey: agentKey,
  manifest,                  // key lookup + price guard
  manifestPriceTolerance: 0, // exact match required
});
```

## Security notes

- The manifest is intentionally **public** — it contains no secret material. The `providerSecret`, payout address, rate-limit internals, and KMS handles are never included.
- The price-guard in `createPaidFetch` protects against a compromised gateway inflating prices in the 402 challenge above what the manifest advertises.
- The manifest's `receiptKeys` array lets a consumer verify receipt signatures without trusting any other source, completing the trust chain: manifest (fetched once, cached) → receipt key PEM → verify Ed25519 signature on each receipt.
- Both manifest endpoints set `Cache-Control: public` with a 5-minute max-age, appropriate for relatively static data that changes only on provider re-registration or key rotation.
